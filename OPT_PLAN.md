# План оптимізації ADHD Planner під Android-only

Зараз застосунок працює в гібридному режимі (web + Android). Ціль - прибрати веб-прототип, спростити код, зробити його більш придатним саме під Android-збірку через GitHub Actions.

## 1. Поточний стан (що є)

| Файл | Стан | Коментар |
|---|---|---|
| `src/index.html` | ~653 рядки, моноліт | Весь UI + логіка + web/Android гілки в одному файлі |
| `src/native.js` | Малий | Тільки проксі для Capacitor плагінів в `window.NP` |
| `scripts/build-web.mjs` | Простий | Бандлить лише `native.js`, копіює `index.html` в `www/` |
| `scripts/patch-android.py` | Готовий | Додає дозволи, іконку сповіщень, версію, вимикає lint для релізу |
| `.github/workflows/build-apk.yml` | Готовий | `npm i` -> `build-web.mjs` -> `npx cap add android` -> `patch-android.py` -> `cap sync` -> `gradlew` |
| `capacitor.config.json` | Готовий | `webDir: "www"`, Android налаштування є |

## 2. Що треба прибрати (Web-only)

Треба видалити або повністю заглушити веб-специфічний код, оскільки збірка йде лише під Android.

| Блок | Рядки (орієнтовно) | Дія |
|---|---|---|
| Google Calendar OAuth | `gtok`, `gexp`, `gis()`, `gAuth()`, `gApi()`, `gConnect/gDisconnect/gSync/gAdd`, `S.g` | Видалити повністю. Залишити лише нативний календар через `@ebarooni/capacitor-calendar` |
| Браузерні сповіщення | `Notification` API, `np` перевірки, веб-бренч у `remSet()`, `notify()` для вебу | Видалити. Використовувати лише `@capacitor/local-notifications` |
| Веб-експорт/імпорт відмінності | Вітка `if(!NATIVE){ const x = document.createElement('a') ... }` в `exportData()` | Уніфікувати під Android: завжди `Filesystem.writeFile` + `Share.share` (як вже частково реалізовано) |
| Умовні гілки `NATIVE ? ... : ...` | Поширені по всьому файлу | Спростити. Більшість з них стане тривіальними після видалення веб-коду. Можна або залишити перевірку `Capacitor.isNativePlatform()`, або прибрати взагалі |
| UI налаштувань під Google | Блоки з `gcon/gsync/gdis` | Замінити виключно на "Календар телефону" (`nSet`) |

## 3. Оптимізація структури коду

Моноліт `index.html` важко підтримувати. Для Android-додатку доцільніше розбити на модулі, не ламаючи поточний CI.

| Крок | Опис |
|---|---|
| **CSS** | Винести весь `<style>` в `src/styles.css`. Підключати в `index.html` через `<link>` або бандлити разом з JS |
| **JS-модулі** | Розбити логіку: `src/state.js` (load/save/migrate), `src/utils.js` (дата/форматування), `src/ai.js` (Gemini + heuristics), `src/notifications.js` (планування `rescheduleNative`, канали), `src/calendar-native.js` (робота з `CapacitorCalendar`), `src/ui.js` (рендер views), `src/app.js` (обробники подій, init) |
| **Точка входу** | Зробити `src/main.js` єдиним entrypoint'ом. Оновити `scripts/build-web.mjs` щоб бандлити не лише `native.js`, а весь `main.js` (або `src/index.js`) через esbuild з `bundle: true` |
| **`native.js`** | Можна або лишити як є (просто проксі), або інтегрувати в модулі напряму через імпорти Capacitor |

`esbuild` вже є в `devDependencies`, тому мінімальні зміни в скрипті бандлингу достатні.

## 4. Оптимізації під Android

| Напрямок | Пропозиція | Причина |
|---|---|---|
| **Сховище** | Перейти з `localStorage` на `@capacitor/preferences` | Більш надійно в Android WebView, менше шансів втрати при очищенні/оновленні деяких оболонок. Зберегти міграцію з поточного ключа `mij-den-v1` |
| **Сповіщення** | Додати дії `Done` / `Snooze 10 хв` до нотифікацій | Згадується в README як "Quick wins". Можна реалізувати через `LocalNotifications.registerActionTypes` + обробник в JS |
| **Точні будильники** | Посилити перевірку `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` | На деяких MIUI/OneUI/EMUI часто блокує. Додати підказку в `remSet()` з прямим переходом в налаштування застосунку (якщо є можливість) |
| **Календар** | Довести до ладу роботу з повторюваними подіями | В README прямо зазначено: "The recurring-events calendar fix is waiting for your confirmation". Варто перевірити логіку `evTimes()` та фільтрацію подій |
| **Ефективність** | Оптимізувати `rescheduleNative()` | Зараз перебирає всі задачі за 14 днів кожного разу. Можна кешувати, планувати лише змінені задачі, не скасовувати всі pending без потреби |
| **UX** | Додати обробку кнопки "Назад" (`@capacitor/app`) | Краще поведінка на Android, зручніше закривати діалоги/повертатись по табах |
| **Статус бар/інсети** | Перевірити `SystemBars` | В `capacitor.config.json` вже є `insetsHandling: "css"`. Треба переконатись, що CSS використовує `env(safe-area-inset-*)` скрізь (частково вже є) |

## 5. Зміни в інфраструктурі збірки

Оскільки збірка через GitHub Actions, зміни мають бути сумісні з поточним workflow.

| Файл | Зміна | Пояснення |
|---|---|---|
| `package.json` | Додати `@capacitor/app` та за потреби `@capacitor/preferences` | Корисні для Android-only UX/сховища |
| `scripts/build-web.mjs` | Переписати під бандл всього JS | Замість `build({ entryPoints: ['src/native.js'], ... })` -> `['src/main.js']` (або об'єднати модулі). Також можна бандлити CSS через esbuild плагін чи просто копіювати |
| `capacitor.config.json` | Без змін або дрібні правки | `webDir: "www"` має залишитись, бо workflow очікує саме її |
| `scripts/patch-android.py` | Можна розширити | Додати перевірку на наявність `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`. Наразі воно і так додає їх, але варто уникнути дублювання |
| `.github/workflows/build-apk.yml` | Швидше за все без змін | Після рефакторингу кроки залишаться тими ж |

## 6. План дій по етапах (реалізація)

Виконувати строго по черзі, щоб не зламати CI.

| Етап | Завдання | Результат |
|---|---|---|
| **0. Аудит** | Повний grep по `gAuth\|gis\|gApi\|gtok\|gexp\|S\.g\|Notification\.requestPermission\|createObjectURL` в `src/` | Чіткий список рядків для видалення |
| **1. Стріп веб-коду** | Видалити Google-блок, браузерні сповіщення, веб-ветки експорту. Залишити лише Android-шляхи. Спрощити умови | Менший, чистіший `index.html` |
| **2. Рефакторинг** | Винести CSS/JS в окремі файли. Переналаштувати `build-web.mjs` на бандл модулів | Модульна структура, легше оптимізувати |
| **3. Android-харднінг** | Міграція на `Preferences` (з fallback на `localStorage`), перевірка дозвіл на точні будильники, дрібні покращення календаря/нотифікацій | Надійніша робота на реальному телефоні |
| **4. Локальна перевірка збірки** | `npm i && node scripts/build-web.mjs` -> перевірити наявність `www/` з `index.html` та бандлом | Переконатись, що бандл зібрався коректно |
| **5. Тест через CI** | Запустити `Збірка APK` в GitHub Actions, встановити на телефон, прогнати чек-лист з README (сповіщення, календар, імпорт) | Фінальна перевірка |

## 7. Ризики та рекомендації

| Ризик | Вплив | Рішення |
|---|---|---|
| **Втрата веб-функціоналу** | Середній | Користувач прямо вказав "I don't need web prototype only android aaplication". Тому видалення Google Calendar веб-версії - виправдане |
| **localStorage -> Preferences** | Середній | Реалізувати зворотну сумісність: спочатку читати з `localStorage`, якщо немає - з `Preferences`, при першому записі мигрувати в `Preferences` |
| **Зміна структури бандлу** | Високий для CI | Не змінювати порядок кроків в `.github/workflows/build-apk.yml`. Лише модифікувати `scripts/build-web.mjs`, щоб він генерував той самий `www/` набір файлів |
| **Дублювання дозволів в Manifest** | Низький | `patch-android.py` вже перевіряє наявність по `android:name`. Можна лишити як є |
| **Календарні рекуренти** | Середній | Не переписувати повністю, спочатку локалізувати й протестувати існуючу логіку `evTimes` + `recurrence` в `ncAdd` |

## Конкретна першочергова задача

Найбільший виграш при мінімумі ризику - **етап 1: стріп веб-коду**. 

Фокус саме на:
1. Видалити весь Google Calendar блок (`S.g`, `gtok/gexp`, `gis/gAuth/gApi`, `g*` функції, UI в `vSet`)
2. Видалити браузерні гілки `Notification` у `remSet()` та `tick()`
3. Уніфікувати `exportData()` під Android-варіант
4. Прибрати зайві `NATIVE` гілки де логіка стала ідентичною
5. Оновити `vSet()` щоб показував лише "Календар телефону", "Нагадування (Android)", "Дані"

Після цього `index.html` скоротиться значно, стане читабельнішим, і далі набагато легше робити модульний рефакторинг.

**Головний принцип:** нічого не міняти в `.github/workflows/build-apk.yml`. Всі оптимізації мають вписуватись в існуючий ланцюжок `build-web.mjs -> cap add android -> patch-android.py -> cap sync -> gradlew`.
